# free-search-mcp test (2026-11-09; 50 FRESH-5 questions, keyless pool, no browser, one query at a time)
Installed in an isolated environment (F:/Projects/tools/fsm_venv, 332 MB, MIT licence, no Chromium). Called directly as a Python function (server.search), max 8 results, cache off. Compared with the DuckDuckGo results cached for the same questions (S19).

Reading.
- Practical: about 4.8 hours for 4,000 sequential queries against about 5.6 hours for DuckDuckGo at the current 5 s limit (an earlier note said 11 hours, which used the old 10 s limit); no key, no credits; two engines failed a few times and the pool recovered. Speed is therefore not a reason to switch.
- Scientific: the evidence is different, not just faster: 80% of queries return a Wikipedia page against 54%, and only 3.1 of 8 URLs are shared. More Wikipedia in the web source makes it more like the local Wikipedia source, which is the loss of independence that cost precision
  in the pinned-page experiments (S22, S23). Switching the search pool would change what "three sources agree" means for the frozen system.
Decision (changed by the user on 2026-11-09): use free-search-mcp for the web source of the new sealed run, because Wikipedia need not be correct or current and the evidence should not lean on it. This is a declared deviation from the certified S19 configuration, which used DuckDuckGo: the frozen system keeps its gate, readers and veto, only the search pool changes, so the SimpleQA certificate does not carry over automatically.
The pilot is run with both pools so the effect of the change is measured. Not used in any reported number so far.
Caveats: 50 queries, one machine, one afternoon; search engines change; scraping several engines may breach their terms and can get an IP blocked (the project's README warns about blocking and about the unauthenticated HTTP transport, which was not used).
